# Development Process

## 1. 프로젝트 개발 방향

컨테이너 반출입 과정에서는 촬영 이미지를 확인하고, 손상 여부를 판단하고, 검사 결과를 보고서로 남기는 작업이 이어진다. 우리 팀은 이 과정을 하나의 흐름으로 연결해 보고자 했다. AI가 손상을 탐지하는 데서 끝나는 것이 아니라, 검사자가 결과를 확인하고 EIR 보고서까지 생성할 수 있는 시스템을 만드는 것이 목표였다.

처음에는 하나의 AI 모델을 중심으로 Cloud에서 이미지를 분석하는 방향을 생각했다. 하지만 실제 게이트 환경을 고려하면서 모든 이미지를 전송하고 분석하는 방식의 부담을 고민하게 됐다. 이후 Edge에서 대상을 선별하고 Cloud에서 상세 분석하는 구조로 방향을 바꿨고, 구현 과정에서는 데이터 전달 방식과 검수 상태, 재검수 범위를 차례로 구체화했다.

실제 게이트 장비 대신 로컬 이미지 simulator로 입력을 재현하며 개발했다. 분석 모듈을 먼저 구현한 뒤 Edge와 Dashboard, 보고서 기능을 연결하면서 개별 기능만으로는 보이지 않던 상태 관리와 연동 문제도 다루게 됐다.

## 2. Architecture Evolution

### Cloud 중심 아이디어에서 Edge + Cloud로

초기 구상은 Cloud 모델이 이미지의 손상 여부와 상세 내용을 함께 판단하는 방식이었다. 구조는 단순했지만, 게이트에서 촬영되는 모든 이미지가 Cloud로 넘어간다면 이미지 전송량과 AI inference 비용을 함께 고려해야 했다.

팀에서는 Cloud 중심 방식과 Edge에서 먼저 선별하는 방식을 검토했다. 우리 프로젝트에서는 손상 의심 여부를 먼저 판단하는 일과 손상의 유형·심각도를 설명하는 일을 나누기로 했다. YOLO가 Edge에서 1차 선별을 맡고, Cloud Foundation Model은 선별된 이미지의 상세 분석을 맡는 구조다.

```text
Gate Image → Edge YOLO → 손상 의심 이미지 선별
           → Cloud Foundation Model → Risk Score → Inspector Review
```

이 결정은 불필요한 Cloud 전송과 분석을 줄이는 방향으로 설계하기 위한 것이었다. 실제 비용 절감률을 측정한 것은 아니며, 게이트 입력과 처리 요구사항을 고려해 분석 위치를 나눈 선택이었다.

Simulator의 일반 입력에서는 YOLO 탐지가 없으면 로컬 로그로 종료하고, 손상 의심 건의 bbox와 confidence를 Cloud로 전달한다. 이벤트 형식 파일명으로 입력한 이미지는 연동 확인을 위해 강제 전송하는 예외 경로도 있다.

### 이벤트 접수와 이미지 업로드 분리

Edge와 Cloud를 연결하면서 이미지와 분석 정보를 어떻게 전달할지도 정리했다. 초기에는 S3 이미지와 별도의 YOLO 결과 JSON을 연결하는 방안을 생각했지만, 이후 이벤트 정보를 API로 먼저 접수하고 이미지는 S3에 직접 업로드하도록 나눴다.

```text
Metadata / YOLO 결과
  → API Gateway → inspection-event-ingest Lambda
  → DynamoDB에 분석 대기 이벤트 생성
  ← S3 presigned PUT URL

검수 이미지
  → presigned URL로 S3 직접 업로드
  → S3 ObjectCreated → analyzer Lambda → Cloud 분석
```

API는 이벤트 ID와 분석 대기 상태, 업로드 위치를 관리하고, S3는 이미지 저장과 분석 시작 이벤트를 맡는다. 이미지 바이너리를 API Gateway와 Lambda 요청 본문으로 전달하지 않도록 해 두 경로의 책임을 분리했다. 실제 전송 이미지는 YOLO bbox를 표시한 JPEG다.

### AI 결과에서 사람의 검수와 보고서까지

초기 분석에서는 위험도가 LOW인 결과를 자동 처리하는 경로가 있었다. 하지만 점수가 낮다는 것과 최종 검수가 끝났다는 것은 별개라고 보고, 분석에 성공한 모든 건을 검사자 확인 대상으로 바꿨다.

Dashboard에서는 이미지와 bbox, 손상 설명, AI 판단 근거를 함께 볼 수 있도록 했다. 검사자는 승인·반려·재검수를 선택하고, 검수 API는 위험 등급 수정도 지원한다. 승인된 건은 `DONE` 상태가 되고, DynamoDB Stream을 통해 보고서 생성 Lambda가 EIR PDF를 만들어 S3에 저장한다.

이렇게 시스템의 목표가 이미지 분석 결과를 보여주는 데서, 사람이 결과를 확정하고 보고서로 남기는 흐름까지 이어졌다.

## 3. 주요 문제와 해결

### 이벤트 접수와 이미지 도착 시점이 달랐다

이벤트를 먼저 저장하고 이미지를 나중에 업로드하는 구조에서는 DynamoDB에 분석 대기 건이 있어도 S3에는 아직 이미지가 없을 수 있었다. 이미지 업로드가 실패하거나 처리가 반복될 때 어떤 상태를 유지해야 하는지가 중요한 문제가 됐다.

분석기는 기존 이벤트의 분석 대기 상태를 확인하고 조건부로 결과를 갱신하도록 바꿨다. 이미 처리된 이벤트가 다시 들어왔을 때 검수 결과를 덮어쓰는 일을 막기 위한 조치였다. 같은 이벤트의 대기 기록만 남고 이미지가 없는 경우에는 새 업로드 URL을 받아 전송을 재개하도록 보완했다.

실패한 분석 건도 Dashboard에서 볼 수 있게 하고, 분석과 보고서를 다시 실행하는 경로를 마련했다. 정상 처리뿐 아니라 중간에 멈춘 작업을 어떻게 이어갈지까지 생각하게 된 계기였다.

### bbox와 손상 목록을 정리해야 했다

YOLO의 중복·중첩 bbox와 Cloud 모델이 가까운 손상을 여러 항목으로 나누는 결과를 정리할 필요가 있었다. Edge에서는 겹침과 포함 관계를 기준으로 bbox를 정리하고, Cloud에서는 같은 유형의 가까운 손상을 병합하도록 했다.

또한 반복 실행의 이벤트 ID 충돌을 줄이기 위해 ID에 촬영 시각을 포함했다. Dashboard 이미지가 안정적으로 표시되도록 조회 시 새 presigned URL을 반영하고, 업로드 이미지의 JPEG 인코딩도 보완했다. 각각은 작은 수정이었지만 전체 흐름을 연결하는 데 필요한 작업이었다.

### Risk Score의 기준을 설명할 수 있어야 했다

처음에는 손상 유형별 가중치와 심각도, confidence를 조합해 점수를 계산했다. 이후 녹, 찌그러짐, 구멍의 차이와 손상 범위를 더 분명하게 반영하도록 유형·심각도·범위에 따른 점수표로 보완했다.

Foundation Model은 손상 정보를 구조화하고, 별도의 규칙 기반 코드가 Risk Score를 계산한다. 여러 손상이 있으면 큰 점수를 중심으로 부가 손상을 약하게 더한다. 모델 설명과 점수 계산을 분리하면서 어떤 입력이 점수에 영향을 주는지 살펴보기 쉬워졌다. 이 점수는 프로젝트의 검수 참고 기준이며, 최종 판정은 검사자가 맡는다.

## 4. Reinspection

### AWS 현업 멘토 피드백을 기능으로 구체화

재검수 기능을 개발하면서 기존 이미지를 단순히 다시 분석하는 것만으로 충분한지 고민했다. 이 과정에서 AWS 관련 현업 멘토로부터 다른 모델을 한 번 거친 이미지를 다시 분석하는 방법에 대한 피드백을 받았다.

팀에서는 이를 이미지 입력을 보완하는 대안으로 검토했다. 같은 이미지를 재호출하는 방식과 비교해, 이미지 보정 단계를 거친 뒤 손상을 다시 판단하는 경로를 마련하기로 했다. 보정과 손상 판정을 나눠 Nova Canvas는 이미지 enhancement에, Claude Sonnet은 실제 손상 분석에 사용했다.

```text
기존 이미지 → Nova Canvas 이미지 enhancement
            → Claude Sonnet 손상 재분석
            → Risk Score 재계산 → 검사자 재확인
```

Nova Canvas는 선명도와 대비 등을 보완하는 이미지를 만들고, Claude Sonnet이 그 이미지를 받아 손상 유형과 심각도 등을 다시 분석한다. 최초 분석과 재검수의 손상 판정에는 같은 Claude 모델 설정을 사용한다. 즉 다른 손상 분석 모델로 교체한 것이 아니라, 다른 모델을 거쳐 보정된 입력으로 다시 판단하도록 바꾼 것이다.

검사자가 재검수 버튼을 누르고 의견을 입력하면, API가 기존 이미지와 bbox를 읽어 이 과정을 실행한다. 새 손상 결과로 점수를 다시 계산하고 DynamoDB를 갱신한 뒤, 결과를 다시 검사자 확인 대상으로 돌린다. 보정에 실패하면 기존 이미지로 분석을 이어가도록 fallback도 넣었다.

### 전체 이미지 재분석에서 기존 bbox 중심으로

처음 구현한 재검수는 이미지 보정 후 전체 이미지를 다시 분석하는 방식이었다. 그런데 재검수의 목적을 생각하면, 새로운 영역을 계속 찾는 것보다 검사자가 확인 중인 기존 의심 영역의 판정을 교정하는 것이 더 적절했다. 전체 재분석은 기존 검수 대상 밖에서도 새로운 손상 영역을 만들 수 있었다.

그래서 기존 결과의 bbox를 우선 사용하고, 필요하면 Edge YOLO bbox를 가져와 재검수 대상 범위를 정했다. 프롬프트에 bbox와 검사자 의견을 함께 전달하고, 반환된 좌표도 기존 bbox에 맞추도록 했다. 전체 이미지는 모델에 전달하되, 프롬프트와 결과 좌표 매핑으로 기존 영역 중심의 재판정을 수행하는 방식이다.

개발 순서로는 **보정 후 전체 이미지 재분석을 먼저 구현하고, 이후 기존 bbox 중심으로 범위를 좁혔다.** 이 변경을 통해 재검수를 단순한 분석 재실행이 아니라, 검사자의 의견을 반영해 기존 판정을 다시 확인하는 기능으로 구체화했다.

이미지 보정의 목적은 재검수 입력을 보완하는 것이며, 보정 전후 정확도 향상을 측정한 것은 아니다. 생성형 보정이 실제 손상 형태를 바꾸지 않는지 살펴보는 일도 앞으로 필요한 검증 과제다.

## 5. 협업과 외부 피드백

Edge 추론, Cloud 분석, 검수 API, Dashboard, 보고서 기능을 나눠 개발한 뒤 팀이 함께 연결했다. 이때 각 모듈이 같은 검사 건을 다룰 수 있도록 `event_id`와 분석 결과, 위험도, 검수·보고서 상태의 필드를 맞추는 일이 중요했다. 샘플 JSON과 데이터 스키마를 공유하며 입력과 출력의 형태를 정리했다.

통합 과정에서는 화면에 데이터가 보이는 것뿐 아니라 상태가 다음 단계로 제대로 넘어가는지도 살펴봤다. Edge의 API POST와 S3 PUT을 실제 AWS에 연결해 확인했고, 중복 이벤트 응답도 점검했다. 이후 분석 상태와 이미지 도착 시점, 실패 건 표시, 이미지 URL 갱신 등을 보완했다. 기능을 붙이고 끝내기보다 연결 과정에서 드러난 문제를 다시 각 모듈에 반영하는 작업이 이어졌다.

두 가지 설계 결정이 특히 기억에 남는다. 하나는 Cloud 중심 아이디어를 실제 게이트 환경에 대입해 Edge 선별과 Cloud 상세 분석으로 나눈 일이다. 다른 하나는 AWS 현업 멘토의 피드백을 받아 이미지 보정과 손상 분석을 분리한 재검수 경로를 만든 일이다.

두 경우 모두 처음 생각한 구조를 그대로 구현하지 않고, 실제로 적용했을 때 어떤 문제가 생길지 팀에서 다시 확인했다. 이후 각 기능이 어떤 역할을 맡아야 하는지 정리하고 실제 코드에 반영했다.

## 6. 배운 점

이번 프로젝트를 통해 모델을 호출하는 코드와 실제 검사 흐름을 만드는 일에는 차이가 있다는 것을 배웠다. Edge가 대상을 선별하고 Cloud가 상세 결과를 만들더라도, 사람이 확인하고 보고서를 남기는 단계까지 연결해야 프로젝트의 목적을 설명할 수 있었다.

또한 이벤트 기반 구조에서는 정상 흐름만큼 중간 상태가 중요했다. 이미지 업로드와 이벤트 저장이 따로 진행되기 때문에 중복 요청과 실패, 재시도를 함께 다뤄야 했다. 각 모듈의 입력·출력뿐 아니라 상태 전이도 팀이 공유해야 한다는 점을 배웠다.

재검수 개발에서는 피드백을 실제 설계로 바꾸는 경험을 했다. 이미지 보정 모델을 추가하는 것뿐 아니라, 왜 보정하는지, 어느 영역을 다시 판단할지, 결과를 누가 확정할지까지 정리하면서 기능의 목적이 더 분명해졌다.

앞으로는 실제 입력 환경에서 전송량과 비용, 탐지 누락, 이미지 보정의 영향을 측정해 보고 싶다. 검사자 인증과 검수 이력 관리도 보완할 부분이다. 이번 개발은 처음부터 모든 구조를 정해 놓고 구현한 과정이 아니라, 기능을 연결하고 피드백을 받아가며 검사 흐름에 맞게 설계를 발전시킨 과정이었다.

상세 구현은 [Architecture](architecture.md), [Data Schema](data-schema.md), [Failure Recovery](failure-recovery.md)에 정리했다.
